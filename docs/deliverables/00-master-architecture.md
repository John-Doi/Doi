## 2. Core Pipeline

```
MISSION REQUIREMENT
   ↓
CAPTURE
   ↓
ORGANIZE
   ↓
PROCESS
   ↓
ANALYZE
   ↓
AI-ASSISTED FLAGGING (where applicable)
   ↓
HUMAN VERIFICATION
   ↓
QA
   ↓
REPORT
   ↓
DELIVER
```

This is a strict superset of the public-facing workflow already on the website (`CAPTURE → ORGANIZE → PROCESS → COMPARE → AI-ASSISTED FLAGGING → HUMAN VERIFICATION → DELIVER`). "ANALYZE" and "COMPARE" are the same step under different names — **use "ANALYZE / COMPARE" internally to avoid a silent terminology fork**; "QA" and "REPORT" are new internal-only stages that sit inside what the website simply calls "DELIVER." No public-facing term needs to change.

## 3. Common DØi Report Core

One report skeleton, reused by every mission-specific module (§26's own goal: "ONE DØi REPORT SYSTEM + MISSION-SPECIFIC MODULES"). The 12-part structure proposed in the Phase 4 brief was evaluated and trimmed — several proposed sections (e.g. separate "Objective/Scope" and "Mission Information") collapse into one without losing anything, and "Results/Findings" and "Annotated Evidence" are combined because findings are never presented without their evidence in a DØi report.

| # | Section | Universal or module-specific | Notes |
|---|---|---|---|
| 01 | Cover | Universal | Logo, title, mission type, DEMONSTRATION label if applicable (§7) |
| 02 | Document Control | Universal | §4 below |
| 03 | Executive Summary | Universal format, module-specific content | Format applied consistently in each product spec's own "Executive Summary" row (e.g. `01-construction-intelligence.md`) and demonstrated in full in `samples/DEMO-construction-intelligence-sample.md`: why the mission was conducted, what was captured, what was produced, the important observations, what the client should review |
| 04 | Mission Information | Universal | Client, site, dates, scope — see Document Control fields |
| 05 | Capture Methodology | Module-specific | Sensors, flight parameters, conditions actually used |
| 06 | Findings + Annotated Evidence | Module-specific content, universal object model | §5 (findings) + §6 (evidence) |
| 07 | Areas of Interest / Review Items | Module-specific | Populated from Finding objects flagged for client attention |
| 08 | QA / Human Verification | Universal | §8 below |
| 09 | Limitations | Universal format, module-specific content | What this mission/method could not establish |
| 10 | Deliverable Index | Universal | List of every file in the delivery package (§9) |
| 11 | Appendix | Optional | Full image index, extended technical notes |

Each product spec (files 01–04) instantiates this core and adds only what's genuinely different about that mission type — it does not redefine the skeleton.

## 4. Document Control

Every DØi report carries this block on page 2, immediately after the cover.

| Field | Description | Source |
|---|---|---|
| DØi Document ID | `DOI-YYYYMMDD-NNN_<PRODUCT-CODE>_v<X.Y>` — see Version Control (§10) | Assigned at report creation |
| Mission ID | The operational mission identifier. **Recommendation, not yet implemented:** adopt `DOI-YYYYMMDD-NNN` (date + daily sequence) as the canonical Mission ID and have the Power Apps mission-checklist system (already referenced in the existing email templates) issue it, so the website's client-facing `DØi-XXXXXX` inquiry reference, the Mission ID, and the Document ID all trace back to one number. This is a follow-up integration item (§12), not something this session can implement without access to that system. |
| Client | Exact client/organization name | Intake / mission record |
| Project / Site | Project name | Intake / mission record |
| Location | Site address | Intake (`Site Address`) |
| Mission Date | Date(s) of capture | Mission log |
| Report Date | Date this document was produced | Report generation |
| Report Version | See §10 | Report generation |
| Prepared By | Analyst/operator name | Internal |
| Verified By | Human verifier name (§8) | Internal QA |
| Document Status | `DRAFT` / `QA REVIEW` / `FINAL` | Internal QA |

**Verification fallback (small-team operation):** independent verification — a different qualified person than "Prepared By" — is the preferred control whenever a second qualified reviewer is available. DØi currently operates as a boutique team, so this spec permits the same qualified individual to both prepare and verify a report when staffing genuinely requires it. That fallback does not relax the verification step itself: verification must still be explicitly and separately performed — reviewing the report against the QA gate (§8) as a distinct pass, not assumed to have happened because the preparer wrote it — and "Verified By" must always name whoever actually did that pass, identical to "Prepared By" or not. This fallback never extends to AI-flagged findings: regardless of staffing model, an AI-flagged finding (`Verification Status: AI-FLAGGED (UNVERIFIED)`, §5) still requires an explicit human verification pass before it can appear in a `FINAL` report.

## 5. Finding / Observation Data Model

One object model, reused across construction, inspection, thermal, and infrastructure work. No per-product duplicate schema.

| Field | Type | Notes |
|---|---|---|
| Finding ID | `OBS-###` (zero-padded, sequential per mission, resets per Mission ID) | e.g. `OBS-014` |
| Area / Asset | Free text | e.g. "North elevation, Building 2" |
| Category | Controlled vocabulary, module-specific (defined per product spec) | e.g. Progress / Condition / Thermal / Spatial |
| Source | `VISUAL` / `THERMAL` / `SPATIAL` / `AI-FLAGGED` / `MANUAL` | How the finding was first identified |
| Observation | Free text, factual/descriptive only | See claim-boundary language in each product spec — **never** an engineering conclusion |
| Supporting Image | Evidence ID reference(s) (§6) | 1 or more |
| Thermal Image | Evidence ID reference, if applicable | Optional |
| Location / Reference | Map coordinate, grid reference, or plain-language location | |
| Priority for Review | `DOCUMENTED` / `REVIEW RECOMMENDED` / `PRIORITY REVIEW` — operational triage, never an engineering/safety classification | See §5 of each product spec for product-specific guidance |
| Verification Status | `AI-FLAGGED (UNVERIFIED)` / `HUMAN VERIFIED` / `REJECTED ON REVIEW` | No finding ships to a client in `AI-FLAGGED (UNVERIFIED)` state — see §7 |
| Notes | Internal-only. Supplemental context tied specifically to *this* Finding that doesn't fit any field above — e.g. a capture-logistics detail relevant to re-visiting the same spot next cycle. Never client-facing. | |

**Notes field scope:** `Notes` exists for one narrow purpose — internal, Finding-specific context with nowhere else to go. It must not duplicate `Observation`, `Category`, `Location / Reference`, `Priority for Review`, or `Verification Status`, and it is not the place for mission-level notes or general QA notes (those belong in the mission record and §8 respectively, not on an individual Finding). If a given Finding has nothing that meets this narrow bar, `Notes` is left blank — it is not a required field, and a report should not manufacture Notes content to fill it in.

`Priority for Review` is deliberately operational language, not a severity/engineering scale — see the claim-boundary sections in each product spec (this is the single most important guardrail in the whole system).

## 6. Evidence / Image Data Model

| Field | Type | Client-facing? |
|---|---|---|
| Image ID | `IMG-###` per mission | Yes (as a caption reference) |
| Capture Date/Time | Timestamp | Yes |
| Mission ID | Reference | Internal only (shown as Document Control field, not repeated per image) |
| Area of Interest | Free text | Yes |
| View / Orientation | e.g. "North elevation, oblique" | Yes |
| Annotation | Markup/callout text on the image | Yes |
| Observation Reference | Finding ID(s) this image supports | Yes |
| Sensor Type | `RGB` / `THERMAL` / `SPATIAL (photogrammetric)` | Yes |

**Internal-only metadata that never appears in a client deliverable unless contractually required:** raw GPS telemetry, aircraft/equipment serial numbers, battery/flight-log identifiers, pilot-in-command records, raw EXIF dumps. These stay in the internal mission record (§11). This is the concrete instance of the "client-facing vs. internal" boundary from §12 of the brief.

## 7. Demonstration Labeling Standard

Every non-client proof asset carries one of these labels, visible on the cover and in the running footer of every page:

- `DEMONSTRATION DELIVERABLE`
- `SAMPLE FORMAT`
- `ILLUSTRATIVE DATA`
- `REPRESENTATIVE OUTPUT`

Rule: a demonstration asset uses a synthetic client name, synthetic Mission ID, and synthetic site — never a real prospect, never real coordinates, never a fabricated technical reading dressed up to look authentic (§20 of the brief — "use `DEMONSTRATION DATA PLACEHOLDER` rather than inventing technical evidence"). See `samples/DEMO-construction-intelligence-sample.md` for the applied pattern.

## 8. QA Model

**Before this is treated as final: confirm with whoever owns the existing internal `QA-01` process whether it already covers deliverable QA or is scoped to flight/operational safety QA only.** This session could not inspect `QA-01` (not in this repository). The checklist below is written to be mergeable into `QA-01` if the scopes overlap, or to stand alongside it as a distinct "deliverable QA" gate if `QA-01` is flight-ops-only.

**Deliverable QA gate — every item must pass before Document Status can move to `FINAL`:**

- [ ] Mission ID correct and matches intake/mission record
- [ ] Client / project name correct
- [ ] Mission date and report date correct
- [ ] All referenced images present and correctly ordered
- [ ] Every image reference (Finding → Evidence) resolves to a real image
- [ ] Annotations match what the image actually shows
- [ ] Finding IDs sequential, no gaps or duplicates
- [ ] Thermal/RGB pairs correct where the product uses both
- [ ] Map/model references correct and current
- [ ] All claims fall within DØi's authorized scope (no survey-grade, engineering-diagnosis, or code-compliance language — see each product spec's claim-boundary section)
- [ ] Every AI-flagged item has been human-verified (no finding remains `AI-FLAGGED (UNVERIFIED)`)
- [ ] No unsupported engineering conclusion appears anywhere in the document
- [ ] Limitations section present and accurate for this specific mission
- [ ] Deliverable Index complete and matches the actual delivery package (§9)
- [ ] Report Version correct per §10
- [ ] Document Status field correct

## 9. File / Folder Delivery Standard

Modular — only the folders a given mission actually produced are included. Nothing is created empty just to match a template.

```
<MISSION-ID>/
├── 01_REPORT/              (the PDF report itself + any exec-summary-only excerpt)
├── 02_IMAGERY/              (RGB, delivered as agreed — raw and/or organized)
├── 03_ANNOTATED/            (annotated/marked-up imagery referenced by the report)
├── 04_THERMAL/              (thermal imagery + RGB-correlation pairs, if applicable)
├── 05_MAPPING/              (orthomosaic/GeoTIFF/spatial outputs, if applicable)
├── 06_3D/                   (point cloud / mesh / model files, if applicable)
└── 07_SUPPORTING_DATA/      (CSV, client-specified formats, anything not covered above)
```

**Naming convention** (no existing DØi convention was found in-repo to reuse, so this is proposed fresh — confirm against the Power Apps mission system before treating as final):

```
<MISSION-ID>_<DocumentType>_v<Version>_<YYYYMMDD>
```

Example: `DOI-20260930-014_ConstructionIntelReport_v1.0_20261002.pdf`

## 10. Version Control

Simple, traceable, no bureaucracy:

- `v0.1` — working draft
- `v0.9` — submitted for QA review
- `v1.0` — final, delivered to client
- `v1.1`, `v1.2`… — corrected/re-issued final (only after delivery; never renumber a version already sent to a client)

Document Status (§4) and Report Version move together: `DRAFT` = v0.x, `QA REVIEW` = v0.9, `FINAL` = v1.x.

## 11. Client-Facing vs. Internal Data

| Stays in the client deliverable | Stays in the internal mission record only |
|---|---|
| Findings, evidence, annotations, maps/models, exec summary, limitations | Equipment/aircraft identifiers, battery and flight logs, detailed airspace/LAANC records, raw pilot notes, internal QA sign-off trail, raw unedited image dumps not needed for the finding they support |

Default to the left column. Only move something to the client column if the mission's contract specifically requires it (e.g. a client that contractually requires flight logs for their own compliance record).

## 13. Dry-Run Validation Plan — shared framework

Every product spec (01–04) fills in this same table for its own mission type — one framework, four instances, not four different validation processes.

| Field | Question it answers |
|---|---|
| Mission Objective | What is this dry run trying to prove? |
| Site Type | What kind of site/asset is used for the test? |
| Required Capture | What sensors/flight pattern does the mission need? |
| Processing | What processing step(s) does the captured data go through? |
| Analysis | What analysis/comparison is performed? |
| QA | Which QA checklist items (§8) get exercised? |
| Deliverable | What's actually handed over at the end? |
| Success Criteria | What has to be true for this dry run to count as a pass? |
| Lessons-Learned Review | Who reviews the result, and what changes to the spec if it fails? |

## 15. Standardization Decision

- **STANDARDIZE NOW:** Common Report Core (§3), Document Control (§4), Finding data model (§5), Evidence data model (§6), Demonstration labeling (§7), QA checklist (§8, pending QA-01 reconciliation), Version control (§10), Client-vs-internal boundary (§11).
- **TEST IN DRY RUN:** All 4 product-specific report architectures, the folder/naming convention (§9) against a real delivery, the Mission ID integration recommendation (§4).
- **AUTOMATE LATER:** Everything in §12 — only after at least one successful dry run per product.
- **REMOVE / NOT NEEDED (this phase):** A fifth report system for sales-only use (§14 shows one architecture already covers it); a bespoke severity/engineering classification scale (deliberately excluded — see claim-boundary sections); building actual PDF/branded templates before the data model survives a dry run.
